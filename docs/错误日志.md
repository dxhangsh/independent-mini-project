## ERR-001 · engine/__init__.py 文档字符串未闭合

- **日期**：2026-09-30
- **环境**：Windows / Python 3.13 / pytest 收集阶段
- **现象**：全部测试收集失败，`SyntaxError: unterminated triple-quoted string literal (detected at line 11)`
- **原因**：写入文件时结尾的 `"""` 闭合丢失（文件被截断）
- **解决**：重写 `engine/__init__.py`；随后对全部源码跑 `python -m compileall` 确认无同类问题
- **预防**：批量写文件后先 `compileall` 再跑测试，把语法层错误挡在最前面

## ERR-003 · merge.py 漏导入 PartGuess

- **日期**：2026-09-30
- **现象**：13 个测试失败，`NameError: name 'PartGuess' is not defined`（`apply_map` 构造返回值处）；API 集成测试里表现为任务线程报 error——**同一根因，两种表象**，排查时被误导绕了弯
- **原因**：移植 `merge.py` 时导入清单只搬了 `part_list, sanitize_part`
- **解决**：补导入；认识到"底层 NameError 会被任务线程的异常兜底吃掉、只报 error"，测试失败时要先看最底层 traceback
- **预防**：移植类文件逐个与原文件 diff 导入清单

## ERR-004 · 原项目 _cut_at_member「、」边界回退分支不可达（移植时发现并修正）

- **日期**：2026-09-30
- **现象**：移植后新写的测试 `build_stem("包装盒、说明书、挂绳、读卡器", max_len=12)` 期望边界裁剪，实际返回 `…挂绳、读`（半个词）
- **原因**：回读原项目源码确认：`cut = s[:max_len]` 恒为 `s` 的前缀，`not s.startswith(cut)` 恒为假，`rsplit` 回退分支是**死代码**——文档声称的"不留半个词"在原项目从未真正生效
- **解决**：移植版改为按成员累积裁剪（与 `sanitize_part` 同思路），首个成员自身超长时才硬切（路径上限是硬约束）；见决策记录 ADR-005，测试同步更新
- **预防**：移植不是复制——文档承诺与代码行为不一致时，以测试逼出真实行为，再决定"忠实保留"还是"修正并记录"

## ERR-005 · 过期 I1 冲突标记误拦 + 批内同名无预检（用户人工验证发现）

- **日期**：2026-10-01
- **环境**：M1 人工验证，真实目录落盘
- **现象**：开发者报告"一直报已阻止落盘，无法确认改名"——在复核页把名字改开后落盘仍被拦截
- **原因**：三个问题叠加——
  1. 方案里存的 `stem_collision` 是流水线当时算的，落盘时原样读取；人工改开后旧标记依然拦截（语义层缺陷）
  2. 对同一文件夹重复执行时，新建议名被磁盘上已有文件占位 → `dst_exists` 物理冲突（本就不可放行，但提示与语义冲突混在一起，无法分辨）
  3. 复核编辑可把两张图改成同一个 final，原预检不查批内重复（仅靠运行时逐条确认 + 自动回滚兜底）
- **解决**：落盘前重算 I1（口径见 ADR-007）；预检新增 `dst_duplicate` 批内同名零写入拦截；前端把三类冲突分开提示并给出对应处理方式，出现可放行冲突时自动放出勾选框
- **预防**：凡是"过程态数据"（issue 标记）要在下游动作中使用时，先问一句"它还成立吗"；混合提示框要按原因分流，不能共用一条红字

## ERR-006 · 编辑工具截断 engine/apply.py 中段（修复 ERR-005 时发生）

- **日期**：2026-10-01
- **现象**：对 apply.py 做局部编辑后，`_rename`/`_append_journal`/`read_journal`/`_undo`/`blocking_issues`/`apply_plan` 六个成员整体消失，但残留代码语法合法——`py_compile` 不报错，测试收集时 `ImportError` 才暴露

## ERR-007 · 保存设置后 Serial 套 Serial，顶栏徽标误显示「云端」（人工实测发现）

- **日期**：2026-10-02
- **环境**：M3 人工实测，真实浏览器（本地 8765）+ 真实 Ollama；pytest 84 例全绿状态下未被覆盖
- **现象**：顶栏状态徽标在打开页面时正确显示「本地 · qwen3-vl:8b」；在设置页点击一次「保存并测试连接」后变为「云端 · qwen3-vl:8b」并持续错误。实际配置始终是 `provider: local_ollama`（config.json 与 /api/settings 均确认）。
- **原因**：`AppState.update_settings()` 执行 `self.serial.swap(build_serial_provider(s))`，而 `build_serial_provider()` 的返回**本身已经是 SerialProvider 包装**（`return SerialProvider(inner)`），导致 `serial.provider` 变成「Serial 套 Serial」；`/api/health` 返回 `state.serial.provider.name` 读到的就成了外层 `SerialProvider.name = "serial"`。前端 `refreshHealth()` 只认 `"local_ollama"`，其余一律显示「云端」。pytest 未覆盖：`conftest.py` 直接 `swap(FakeProvider)`（不经 update_settings），真实路径被跳过。
- **解决**：最小修复——`update_settings` 改为 `self.serial.swap(build_serial_provider(s).provider)`，只 swap 内部 Provider，保持 `serial.provider` 始终是真实 Provider（本地/云端）。新增回归测试 `test_health_provider_after_save_settings`（保存后 health.provider 必须为 `local_ollama`，修复前为 `serial`）。**85 例全绿**；重启服务后浏览器实测：重载与保存设置后徽标均正确显示「本地 · qwen3-vl:8b」。
- **预防**：包装类（SerialProvider）的 swap 目标必须是「被包装对象」而非「包装本身」；「保存类操作后读状态」的前端路径要进集成测试；人工实测的「保存→刷新→核对徽标」步骤保留为每次发布前冒烟项

## ERR-008 · run.ps1 解析报错：UTF-8 无 BOM 遇上 PowerShell 5.1（用户启动报错）

- **日期**：2026-10-07
- **现象**：用户启动 `run.ps1` 报错；复现为 `run.ps1:33` 解析器错误"表达式或语句中包含意外的标记'}'"
- **原因**：脚本是 **UTF-8 无 BOM** 编码，Windows PowerShell 5.1 按 ANSI(GBK) 误读中文内容，某个多字节序列破坏了 `if ($Lan) {` 块的语法结构，33 行的 `}` 于是成了"意外标记"。9/30 的旧版脚本同样无 BOM 却能跑——属中文字节序列的运气差异；加入 `-Lan` 分支后字节内容变化即触发。排查中已排除执行策略（本机 Unrestricted）、端口占用、脚本被复制挪位三种假设
- **解决**：重写 run.ps1（提示语改英文、中文仅留注释）并**强制写入 UTF-8 BOM**；用 `Parser::ParseFile` 做静态解析检查（0 错误）+ 实跑验证（8765 正常监听、health OK）；另附纯 ASCII 的「启动 PicNamer.bat」双击启动器，同时免疫编码与执行方式问题
- **预防**：Windows 下含非 ASCII 字符的 `.ps1` 必须带 BOM（PS 5.1 无论 `-File` 还是"使用 PowerShell 运行"都按 ANSI 读无 BOM 文件）；发布脚本前用 `Parser::ParseFile` 做静态解析检查；双击启动场景优先提供 .bat 包装

## ERR-009 · 目录内容变动后仍列出旧图（本人实测 + 用户报障）

- **日期**：2026-10-07
- **环境**：M3 收尾自测，真实目录 + 浏览器
- **现象**：处理路径的图片有变动（替换/增删）后无法即时响应——复核页仍显示老图片；重提交同批目录也出不来新扫的图
- **原因**：两层根因叠加——
  1. 缩略图响应头 `Cache-Control: private, max-age=3600`：同名路径文件被替换后 URL 不变，浏览器 1 小时内直接用旧缓存图
  2. 批量"重提交跳过已完成目录"（断点续跑设计）无条件沿用旧方案快照，目录内容变了也不重扫
- **解决**：缩略图改为 ETag（mtime_ns+size）再验证 + `no-cache`，服务端内存缓存按内容键失效；批量 `submit` 对 done 目录比对内容签名（图片名+大小+mtime_ns），有变动自动作废旧快照重新处理；`resume()` 保留纯续跑语义（ADR-010）；复核页显示快照生成时间
- **预防**：给响应设置长缓存前先问"这个 URL 的内容会不会变"；"跳过已完成"类优化必须与"内容新鲜度"场景分开设计；改动静默缓存行为时补带内容变更步骤的回归测试（本例新增 4 例）

## ERR-010 · 修完"列表过期"用户仍见旧界面：SW 缓存优先顶住新前端（交付层失误）

- **日期**：2026-10-07
- **现象**：ERR-009 修复后用户反馈"即时刷新不管用"。后端修复（ETag/签名重扫）经测试证明有效，但用户浏览器端仍可能拿到旧界面
- **原因**：两层交付失误叠加——
  1. 修改了前端（index/app.js/css）却**没有把 sw.js 的 CACHE 版本号 +1**：Service Worker 对静态资源是缓存优先，浏览器持续用安装时缓存的旧 app.js/页面，新功能根本没到达用户（README 里自己写的规则自己没执行）
  2. 后端改动需要重启服务才生效，用户侧未必重启
- **解决**：CACHE v1→v2；**SW 策略整体改为网络优先、离线回落缓存**（本地常驻迭代的应用，新鲜度优先，缓存只作离线兜底）——从机制上根治"旧前端顶住新版本"这一类问题；新增单目录「重新扫描」按钮（/api/batch/rescan），目录变动的刷新不再依赖重新提交路径
- **预防**：SW 存在时，"改了前端"必须问一句"用户怎么拿到新版"；能靠策略（网络优先）解决的不要靠纪律（记得 bump 版本号）；每次交付前端改动，重启后端 + 强刷两步写进操作指引

## ERR-011 · fpdf2 2.8.9 对齐/换行限制三连（报告 PDF 生成踩坑）

- **日期**：2026-10-07
- **现象**：报告 PDF 渲染连续三处 `FPDFException: Not enough horizontal space to render a single character`；改完后 `pdf.table()` 又报 `col_widths_ratio` 参数不存在
- **原因**（逐一实测定位）：fpdf2 2.8.9 中——
  1. `multi_cell(markdown=True)` 仅兼容 `align="L"`，J/R/C 一律在换行计算时崩溃
  2. `align="C"` 即使不用 markdown，只要文本**发生换行**同样崩溃（单行居中正常）
  3. 表格相对列宽参数在 2.8.x 已改名 `col_widths_ratio` → `col_widths`
  最小复现探针逐组合验证排除，锁定为库版本行为而非用法错误
- **解决**：正文加粗改用 `write()` 流式排版 + 手动字体切换（绕开 markdown 解析）；居中内容只允许**单行 `cell`**（预检宽度，超宽自动降级左对齐）；表格参数改名；`char_wrap="CHAR"` 移除（默认模式已能按字符断行 CJK）
- **预防**：选库先看目标版本的 API 变更日志；遇到"神秘空间不足"先用最小探针做组合矩阵排查（本次 3 组对照 10 分钟定位），不要在业务代码里盲试
